## Technical discoveries

- **2026-09-21** — Real Google Chrome (branded) ignores `--load-extension`, so extension e2e tests must run in Playwright's Chromium (`channel: 'chromium'`). Found in the old API Mock Master project and reused here.
- **2026-09-22** — Task 11 verification run: `npx playwright test` → 95 passed, 0 failed, in about 1.3 minutes (single worker, real Chromium via `channel: 'chromium'`).
- **2026-09-22** — `test/helpers.js`'s `pushRules()` hard-codes a 20ms wait after posting `RULES` into the page before returning; flagged as a latent flakiness risk as early as Task 1's review. By Tasks 9 and 10, two independent implementer runs saw intermittent failures in `test/engine-fetch.spec.js`/`test/engine-xhr.spec.js` (a different test failing each time) — though the controller's own three full-suite runs after Tasks 9 and 10 were all clean (92/92, 95/95, 95/95), matching this task's own clean 95/95 run. At the time, the wait itself was suspected as the cause. **Correction, 2026-09-22 (final-review fix wave):** that diagnosis was wrong, and a longer/poll-based wait cannot fix it. The real cause is a race with the *real bridge*: on every page load `bridge.js` independently reads `chrome.storage.local.get('state')` and pushes whatever it finds (empty, in these `openWithRules`-style tests, since nothing wrote state) into the engine as `RULES: []`; when that async bridge push lands *after* the test's own direct `pushRules()` call, it silently wipes the test's rules, regardless of how long `pushRules()` waited before returning. Reproduced directly by delaying only the bridge's initial storage read. Fixed by seeding `chrome.storage.local` via `setState(serviceWorker, { rules })` before `context.newPage()` in every test that opens a page against the real extension (`test/engine-fetch.spec.js`, `test/engine-xhr.spec.js`, `test/smoke.spec.js`), so the bridge's storage-derived push and the test's direct `pushRules()` push always carry the same rules — nothing is left to race.

The literal on-screen toolbar badge was not visually inspected (see the check-1 entry for why).

## Key decisions

- **2026-09-21** — The engine's `RULES` listener uses the capture phase: at the target, capture listeners run before bubble listeners, so a bubble-phase engine listener could not hide the message from a page's capture listener.
- **2026-09-21** — Gate, fail-open and privacy tests use a plain Chromium page with only `engine.js` injected (`enginePage`): with the real bridge present, `RULES` arrive within milliseconds and the startup gate could never be observed.
- **2026-09-21** — A `MOCK_EVENT` is emitted when a rule matches, before the delay, as the spec says. If building the response then fails, an `ENGINE_ERROR` follows for the same request (rare; accepted).
- **2026-09-22** — `engine.js`'s XHR `open()`/`send()` wrap internal bookkeeping in bare `catch (_) {}` blocks that swallow any exception, not just expected matching failures (flagged in Task 5's review). Accepted: it mirrors an already-approved pattern from the fetch-mocking code in Tasks 3-4, and the brief's own next task upgrades the `send()` matching-failure catch to call `reportError(e)` (confirmed present in `engine.js`'s XHR `send()`). The remaining bare catch, around `xhrRequests.set(...)` bookkeeping in `open()`, is intentionally silent because it wraps operations that cannot throw on valid input.
- **2026-09-22** — `background.js`'s hit-count map (`hits`) is updated from two independent, unserialized code paths — `MOCK_EVENT` (via the per-tab event queue) and `DELETE_RULE`'s hit-cleanup (via a separate promise chain) — leaving a few-millisecond window where deleting a rule at the same instant a matching request completes can orphan a stale `hits[ruleId]` entry (flagged in Task 9's review). Accepted: the window is narrow, the only consequence is inert data nothing ever reads again (the UI only looks up `hits` by a rule id that still exists in `state.rules`), and the spec already treats hit counts as best-effort with an equivalent-severity gap (debounced flush lost on abrupt service-worker shutdown). Left as a known limitation; a future task could close it by wrapping `DELETE_RULE`'s hit cleanup in the same `enqueue()` used by `CLEAR_LOG`.
